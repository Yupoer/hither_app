# 離線旅程與耗電修正驗證（#272）

## 交付範圍與限制

- 目標：iOS production 交付。原始旅程修正是 OTA-safe；因 CI 發現既有 Expo SDK 56 原生 patch 依賴落後，已另外更新相容 patch 版本，因此本次需先建立並驗證新的 iOS binary，再發布同 runtime 的 OTA。
- 旅程操作先取得本機持久化收據，再嘗試傳送；收據不代表隊員或後端已收到。
- 網路、結果不明的逾時、登入狀態、隊長資格、後端存取拒絕、輸入錯誤與本機儲存失敗分開顯示。未知原因不能推定為權限問題。
- 使用者不要求本次實體裝置測試。本文件及自動化測試不能證明半小時耗電量、溫度或音樂播放已改善。

## 同步規則

- 同一帳號／團隊的操作依序處理；暫時失敗或待處理衝突阻擋後續相依操作，不阻擋其他團隊。
- 重送保留操作 UUID；本機序號只描述本機先後，不可拿來判定不同裝置的操作相同。
- 相同地點只在可信 provider ID、團隊／分隊、日期、種類相同且尚未完成時合併。座標相近不是合併依據；已完成地点可再次造訪。
- 衝突採後端現況，本機草稿保留供使用者選擇。放棄或重新套用會取消相依操作；重新套用建立新的操作 ID。
- 切換帳號不能提交另一帳號的草稿，也不能把另一帳號的草稿標成無效。
- 到達判斷使用原始、未過期且精度足夠的定位；新目標與同 ID 的座標變更都觸發重算。已在抵達半徑內不播放過時的接近提示。

## 有程式測試的工作量上限

- 一般旅程定位上傳最短間隔 10 秒；移動心跳 15 秒、靜止心跳 60 秒。只有明確開啟精準模式才使用 5 秒上傳下限。
- 地圖位置畫面更新與定位判斷分開；減少畫面重繪不得停止靜止時的新目標抵達判斷。
- 路線服務失敗採共用冷卻與有限探測，不能因座標持續改變就繞過冷卻。
- Realtime 正常時群組補讀每 5 分鐘；連線失敗時退避，單次補讀完成後才排下一次，背景停用。
- 粒子速度 ×0.5、閃爍頻率 ÷3、密度 ×0.5、半徑 ×1.5；透明繪製在原有 Liquid Glass 上方、文字與控制項下方。動畫最高 30 FPS，低耗電模式 15 FPS，背景／減少動態／已觀測到嚴重熱狀態時停止。
- 熱狀態來自既有原生效能取樣，沒有新增原生即時熱狀態監聽器。未取樣或原生能力不存在時，不能宣稱已知裝置溫度。
- 診斷上傳仍須使用者同意；效能防護與錯誤分類不要求開啟完整診斷追蹤。

## 發布前檢查

1. 全部 Jest、TypeScript、parent 272 acceptance-map、改動程式函式覆蓋率門檻。
2. 真正 SQLite 的 schema 升級、交易回滾、帳號隔離、FIFO 與中斷復原。
3. 真正 PostgreSQL 的既有抵達／未排程地點與新 durable RPC；檢查權限、相依操作、重複操作、相同 provider 合併及版本衝突。
4. 生產 schema 前置 migration 與實際函式狀態核對；不能只看 Git 上有 migration 就假設生產已部署。
5. iOS export、與已安裝 runtime 的原生相容性檢查、獨立審查、master 遠端 SHA、OTA group／平台／runtime 回查。

補部署缺少的舊 migration 時，必須核對它是否會覆寫後來已部署的安全修正；不可僅依「缺少 migration」清單盲目套用。正式環境本次仍未部署。發布前須以正式函式定義與後續安全 migration 核對套用順序。

## 後端觀測的解讀

本次唯讀紀錄同時出現路線代理 503、資料表／函式 42501，以及 28000／401。這些是不同錯誤類別，不應共用「確認你是隊長」。它們支持修正重試與錯誤對照，但不足以單獨證明 CPU、記憶體、定位或 GPU 是電量快速下降的唯一原因。現有後端紀錄缺少可對應該次裝置行程的連續電量／CPU／溫度樣本；不將程式上限或單元測試換算為節電百分比。
