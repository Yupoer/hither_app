# Optional graphics and diagnostic attribution (#281)

Settings → Support section contains the existing native `SystemToggle` for diagnostic consent. The saved choice remains opt-in. Enabling grants capture after persistence succeeds; disabling immediately closes the gate, stops collection and purges pending records. A storage failure is reported and capture stays off for that session.

Each upload batch captures the current consent revision. Revoking consent stops subsequent payloads, aborts pending diagnostic request signals (including requests waiting for token lookup or auth recovery), and re-enabling cannot revive an obsolete batch. A request already accepted by the server before revocation cannot be withdrawn.

The iOS bridge observes system thermal and Low Power Mode notifications independently of upload consent, reads initial state before registering thermal notifications, and refreshes state when the app becomes active. This safety path neither samples sensors on a timer nor stores/uploads diagnostic records. Partial native runtimes remain usable with static optional visuals. Optional shader/starfield and map marker interpolation/pulses run only with known nominal thermal state and Low Power Mode off; other states stop animation. Location, synchronization, retries and fresh marker coordinates retain their cadence. Fullscreen shader updates are capped at 20 FPS, and hidden/background canvases unmount.

Consent-enabled reports retain the existing finite startup burst and five-minute steady cadence. Thermal changes and foreground resume can request a foreground one-second native sample, throttled to one incident sample per 30 seconds; small thermal transition records preserve state changes and the previous state's dwell time even within that throttle or while backgrounded. Reports use the existing allowlist, SQLite retention cap and batch uploader. There is no continuous JS frame monitor in this low-overhead path.

| Report fields | Meaning and limits |
| --- | --- |
| `cpuTimeKind`, `cpuTimeMs`, `cpuCorePercent`, `cpuPercent`, `sampleWindowMs` | iOS one-second burst CPU delta, raw core-equivalent percentage (100% means one core), active-core normalized percentage and actual elapsed sample window. Android explicitly labels its process counter cumulative. |
| `processCpuTimeMs`, `processSampleTimestampMs`, `cpuIntervalDeltaMs`, `cpuIntervalWindowMs`, `cpuIntervalCorePercent`, `cpuIntervalNormalizedPercent` | Cumulative process CPU including exited iOS threads, its native timestamp, and deltas between samples. The first sample/unsupported binary reports null interval values. Interval CPU includes background work; foreground/background durations provide context. |
| `mainThreadDelayMs`, `jsSchedulingDelayMs`, `uiFps`, `frameTimeP95Ms`, `missedFrameRatio` | Native main-queue enqueue/finish lateness, one 100ms JS scheduling probe, display timing. Missed frames compare against CADisplayLink's effective target cadence, including adaptive refresh. These are bounded probes, not a continuous stall trace. |
| `memoryMb`, `memoryDeltaMb`, `sampledMemoryPeakMb`, `memoryWarningCount` | Physical footprint, delta between samples, maximum observed start/end footprint and consent-session memory warnings. Sampled peak is not an authoritative peak between samples; MetricKit daily memory metrics remain the source for that peak. |
| `shaderCanvasCount`, `starfieldCanvasCount`, `animatedCanvasCount`, `mapCount`, `memberMarkerCount`, `destinationMarkerCount`, `mountedCardCount`, `rawRoutePointCount`, `displayRoutePointCount`, `markerMotionEnabled` | Current mounted/active rendering workload counts, released with their owning component. No coordinates or user/device identity are added. Mounted map counts exclude background; marker counts describe mounted marker data. |
| `routeProjectionCount`, `routeProjectionDurationMs` and existing render/location/realtime/route/request counters | Counts and total route trim/LOD computation time since the prior diagnostic counter snapshot; counter window is separately labelled. |
| `thermalPreviousState`, `thermalState`, `thermalDwellMs`, `nativeAppVersion`, `nativeBuildNumber`, `hardwareModel` | System transition context and reliable binary/hardware categories. These fields do not include a unique device identifier. |

MetricKit energy signposts use its log handle and `mxSignpost` so supported system reports can include operation resource metrics. Unsupported instantaneous per-process GPU usage is not invented. Existing MetricKit CPU/hang diagnostic payloads and stacks remain available through the consented pipeline.

Native additions require a compatible binary. App version, runtime and checked-in iOS configuration are aligned at **0.1.9**; no OTA, binary build, upload or store submission is part of this change. Windows automated checks verify JS behavior and native source contracts, not Swift compilation or actual-device temperature/audio/battery behavior. Device acceptance must compare the same workload with diagnostics on/off, record thermal transitions/CPU/memory, and verify stable UI plus uninterrupted background audio. The policy aims to keep optional work within nominal operation; software cannot guarantee the system will always remain nominal under all environments or hardware workloads.
